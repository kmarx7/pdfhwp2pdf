# 실제 Word 레이아웃 검토와 부분 보완

검토일: 2026-10-24~25. 브랜치 `fix/hwp-layout-fidelity`.

## 결론

사용자가 지정한 다운로드 DOCX는 직전 전달 파일과 ZIP 내부 모든 part의 내용이 같았다. 새 파일 이름이나 다운로드 중 손상 문제는 아니었다. **원본 레이아웃 보존 품질이 부족했다.** 실제 한글 뷰어에서는 원본 **16쪽**, Word에서는 기존 결과 **8쪽**으로 표시됐다. 글꼴 대체, 줄바꿈, 표 높이와 페이지 배치가 달랐다. 직전의 문자 coverage 1.0·표 38개·다운로드 성공은 시각 품질 합격이 아니다.

## 확인한 엔진 원인

고정 hwp-cli v1.3.1의 DOCX writer는 소스 주석에서도 내용 중심이고 페이지 레이아웃 복원 엔진이 아니라고 명시한다. [고정 writer](https://github.com/STAIxBWLB/hwp-cli/blob/v1.3.1/crates/hwp-convert/src/docx.rs)

- 빈 문단을 생략한다. 원본의 문단별 수직 간격과 서식 작성 공간이 줄어든다.
- 문단 `break_type`의 강제 쪽 나눔을 DOCX로 내보내지 않는다.
- 비율 줄 간격이 기본 160이면 문단 속성을 생략하여 Word 기본 간격이 적용된다.
- HWP의 상·하 여백과 머리말·꼬리말 영역의 합을 Word 본문 여백에 반영하지 않는다.
- 셀의 세로 정렬·최소 행 높이를 옮기지 않는다.
- 원본 이름의 글꼴이 Word에 없으면 대체된다. 한글 뷰어와 Word가 서로 다른 글꼴로 대체하기도 한다. 글꼴 이름을 XML에 적었다는 사실은 같은 화면을 보장하지 않는다.

현재 최신 공식 릴리스도 v1.3.1임을 확인했다. 무검증 업그레이드로 해결됐다고 가정하지 않는다. [공식 최신 릴리스](https://github.com/STAIxBWLB/hwp-cli/releases/latest)

## 이번 코드의 부분 보완

`HwpLayoutPostProcessor`는 기존 paragraph/run/table 개체를 재사용한다. 원본 문단과 결과 문단의 텍스트를 순서대로 대응하고, 대응 불일치는 실패시킨다. 빠진 빈 문단과 강제 쪽 나눔, 160%를 포함한 비율 줄 간격, 본문 여백, 셀 세로 정렬과 단일 행 셀 기반 최소 행 높이를 복원한다. 행 높이는 `atLeast`이며 잘림을 만드는 강제 고정 높이를 사용하지 않는다. 병합된 모든 행 높이·부유 배치·제목 스타일·글꼴 대체의 완전 복원은 하지 못한다.

사용자 원본의 후보에서 빈 문단 179개(셀 내부 포함)와 강제 쪽 나눔 6개를 복원했다. 후보가 실제 Word에서 복구 대화상자 없이 열리는 것은 확인했으나, 화면 표시 페이지 수는 13쪽/후속 후보 12쪽으로 원본 16쪽과 달랐다. 이 값은 각 후보를 연 시점 Word UI의 값이며, 최종 PDF 렌더 전체 검증 결과가 아니다. **새 후보를 완성본으로 전달하지 않는다.**

품질 보고서에 `hwp_layout_hints`를 추가하고 강제 쪽 나눔 누락을 검사한다. `visual_fidelity_verified`는 `false`이며 실제 페이지 수 일치를 뜻하지 않는다. UI와 API 경고는 HWP 결과를 편집용 초안으로 설명한다.

## 대체 경로 조사에서 발견한 PDF 글꼴 오류

한글 뷰어에서 원본 16쪽을 텍스트가 포함된 PDF로 출력해 비교했다. 이 PDF의 일부 글꼴 subset에는 family name과 OS/2 테이블이 없었다. pdf2docx 0.5.13은 이때 family를 빈 문자열로 덮어쓴 뒤 예외를 처리해, 모든 Word run의 글꼴명이 비는 문제가 있었다.

`SafeFonts` 어댑터는 family가 없으면 원래 PDF 글꼴명을 유지하고, 빈 descriptor가 다른 모든 글꼴과 매칭되지 않게 한다. 설치된 라이브러리 파일은 수정하지 않는다. 변환이 단일 격리 worker에서 실행되는 동안만 의존성의 Fonts 참조를 교체하고 finally에서 복원한다. 기존 lock에 있는 `fonttools==4.67.0`을 명시적 의존성으로 기록했다.

실제 PDF 경유 후보에서 902개 run의 빈 글꼴명이 네 종류의 PDF 글꼴명으로 복원됐지만, Word 화면의 절차 표가 어긋나 **이 경로도 품질 합격으로 채택하지 않았다**. 로컬 기존 글꼴의 editable embedding 플래그를 확인한 별도 글꼴 포함 후보도 조사했으나 동일 표시 보존을 증명하지 못했다. 글꼴 파일을 시스템에 설치하거나 저장소에 추가하지 않았다. 이 수동 실험은 웹앱의 자동 HWP→PDF 지원이 아니다.

## 자동 검증과 남은 작업

`.venv/bin/python -m pytest -q` → **85 passed, 6 warnings in 14.59s**. 새 합성 HWP로 빈 문단·강제 쪽 나눔·160% 간격·본문 여백·최소 행 높이/세로 정렬을 검사했다. 이름/OS2가 없는 글꼴 fixture로 빈 글꼴명 회귀를 검사했다. 이 테스트들은 원본 16쪽의 Word 시각 품질을 합격 처리하지 않는다.

원본 HWP와 기존 다운로드 DOCX는 덮어쓰지 않았다. 원문·모델·검토 후보·기준 PDF·글꼴 포함 후보는 `runtime/layout-review/`의 git 제외 QA 자료로만 두며 자동 1시간 만료 대상이 아니다. 재검토/수동 정리 전까지 로컬에 보관한다. 정상 API 작업의 입력 삭제·결과 1시간 수명 정책은 유지한다.

다음 구현 관문은 올바른 글꼴/대체 글꼴 환경을 확정하고, 원본의 실제 페이지별 배치와 Word 렌더를 대응한 후 전체 페이지에서 표·줄바꿈·잘림·서식 차이를 검증하는 것이다. 현재처럼 내용 중심 writer의 성공 여부만으로 원본 레이아웃 보존 엔진을 활성화해서는 안 된다.
