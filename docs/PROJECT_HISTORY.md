# 문서잇 프로젝트 대화·개발 기록

작성일: 2026-10-27. 지금까지의 사용자 요청, 구현 결과, 결정과 제한을 정리한 작업 요약이다. 대화 원문 전체를 복사한 문서는 아니다. 개인 문서의 본문·원본 파일명·절대 경로와 글꼴 파일은 포함하지 않는다.

## 현재 상태

Python 기반 로컬 웹앱 **문서잇**을 구현했다. 최신 기능이 함께 포함된 브랜치는 `feat/upload-convert-actions`이며, 이 기록 작성 직전 기능 커밋은 `b551cac`이다. 원격 저장소는 <https://github.com/kmarx7/pdfhwp2pdf>다. 기능 변경은 별도 브랜치에서 작업하고 테스트·커밋·푸시하는 방식을 사용한다.

| 기능 | 현재 제공 상태 | 중요한 제한 |
| --- | --- | --- |
| PDF → Word | PyMuPDF 분석 → pdf2docx → DOCX 후처리·검증·다운로드 | 텍스트 기반 PDF 중심, 복잡한 배치 품질 미검증 |
| HWP → Word 직접 변환 | 고정 hwp-cli 1.3.1과 표·쪽 번호·일부 배치 후처리 | 편집용 초안이며 원본 배치 보존 미완료 |
| HWP → Word 권장 경로 | native-embedded 경로를 웹 기본 모드로 제공 | 같은 HWP의 한글 출력 기준 PDF 필요 |
| HWP → PDF | 별도 버튼과 실제 hwp-cli PDF 출력·검증·다운로드 | 한글 뷰어 인쇄와 다른 렌더러, 실험 기능 |
| 바탕화면 실행 | macOS 문서잇.app 아이콘 배치 및 실행 확인 | 프로젝트 폴더와 .venv가 현재 위치에 있어야 함 |
| 다운로드 폴더 열기 | 다운로드 요청 뒤 macOS Finder 기본 Downloads 열기 | 브라우저 저장 완료/사용자 지정 경로는 알 수 없음 |
| 다운로드 파일명 | 원본 이름을 유지하고 확장자만 변경 | 이름 없는 예전 작업은 다시 변환해야 함 |
| 업로드·변환 동선 | 두 버튼을 업로드 영역 아래에 인접 배치 | 아주 좁은 화면은 같은 묶음 안에서 세로 배치 |
| 새 파일 연속 변환 | 완료 후 다운로드 옆 새 파일 업로드 버튼 | 새 파일을 실제 선택하면 이전 작업을 정리 |
| HWPX·OCR·HWP 편집기 | 미구현 | 지원 기능으로 표시하지 않음 |

## 요청과 작업 경과

### 설계와 PDF MVP

사용자는 PDF·HWP·HWPX를 편집 가능한 DOCX로 바꾸는 Python 웹앱을 요청했다. 최우선 목표는 본문·문단·글꼴·표·이미지·페이지 설정의 보존이며, PDF 페이지 전체를 이미지로 Word에 넣는 방식은 금지했다.

먼저 라이브러리의 실제 지원 범위와 Apple Silicon 호환성, 엔진 교체 구조, API, 파일 수명, 품질 지표와 테스트 계획을 문서화했다. 설계 문서는 [PRD](PRD.md), [ARCHITECTURE](ARCHITECTURE.md), [CONVERSION_SPEC](CONVERSION_SPEC.md), [TEST_PLAN](TEST_PLAN.md), [AGENTS](../AGENTS.md), [README](../README.md)다.

이후 PDF → DOCX MVP를 구현했다. FastAPI, 한국어 HTML/CSS/JavaScript 화면, 드래그 앤 드롭, 업로드 유효성 검사, 격리 변환 worker, 진행 상태·오류·다운로드와 작업 정리를 제공했다. 실제 생성한 텍스트·표 PDF로 편집 가능한 Word 텍스트/표 개체를 검사하고 손상·암호화·스캔 PDF 오류를 처리했다. 상세 증거는 [PDF MVP 보고서](STAGE2_REPORT.md)에 남겼다.

사용자는 원격 저장소를 지정하고 Git 푸시 및 기능별 브랜치를 요청했다. 이후 작업은 해당 방식으로 진행했다.

### HWP 베타와 레이아웃 문제

사용자가 HWP 변환 기능이 없음을 지적해 HWP 5 베타를 추가했다. 실제 고정 엔진 hwp-cli 1.3.1을 프로젝트 내부에 설치하고, 본문·기본 표/병합·이미지·일부 글꼴/스타일을 직접 DOCX로 옮겼다.

실문서에서 미지원 요소 오류가 이어져 감지한 요소와 실패 사유를 구체화했다. 쪽 번호의 제한된 PAGE 필드 변환, 표 너비·테두리·단색 배경, 일부 그라데이션의 단색 근사와 배치 힌트를 후속 보완했다. 미지원 요소를 무조건 무시하거나 실패를 성공으로 바꾸지 않았다.

실제 Word 검토에서는 원본 16쪽이 기존 직접 변환 DOCX에서 8쪽으로 표시돼 레이아웃 품질 미달이 확인됐다. 일부 후처리를 보완해도 원본과 동일한 글꼴·줄바꿈·표·페이지 나눔은 재현하지 못했다. 따라서 직접 경로를 **편집용 초안**으로 설명한다. [HWP 보고서](HWP_REPORT.md), [표 서식 보고서](HWP_TABLE_REPORT.md), [레이아웃 검토](HWP_LAYOUT_REVIEW.md)를 참고한다.

### native-embedded 결과 채택과 웹 연결

사용자는 여러 결과 중 native-embedded가 원본과 비슷하게 잘 나왔다고 평가했다. 이에 해당 경로를 우선 기준으로 채택했다.

```text
원본 HWP
  → 한글 뷰어에서 전체 페이지를 텍스트가 포함된 PDF로 저장
  → pdf2docx로 편집 가능한 Word 텍스트·표 복원
  → 로컬 글꼴 포함
  → 구조 검증 후 DOCX 제공
```

처음에는 로컬 CLI로 재현 가능하게 정리했고, 이후 사용자가 웹에서도 같은 결과를 요구해 HWP 웹 기본 모드를 native-embedded로 연결했다. 등록된 같은 HWP 해시의 PDF를 사용하거나 사용자가 기준 PDF를 첨부한다. 기준 PDF가 없거나 본문이 부족하면 이유를 표시하며 직접 초안으로 자동 전환하지 않는다.

당시 사용자 문서의 기준 PDF는 16쪽이었다. 웹에서 실제 변환·다운로드한 결과는 사용자가 선호한 후보와 본문 `word/document.xml` 및 font alias별 regular/bold 연결의 글꼴 데이터가 동일했다. HWP→기준 PDF와 기준 PDF→DOCX 문자 포함률은 각각 1.0, Word 표 69개, 포함 글꼴 6개를 확인했다. 약 52MB 결과의 선호 후보는 이전 Word 확인에서 18쪽이었다.

이는 **선호 후보 재현 확인**이며 원본과 모든 페이지의 시각 배치가 일치한다는 뜻이 아니다. 문자 다중집합 검사는 읽기 순서를 증명하지 않고, Word 전 페이지의 새 시각 비교·편집/저장 관문은 남아 있다. 기준 PDF 등록은 24시간 유효하므로 과거 등록 완료가 현재 이용 가능을 뜻하지 않는다.

사용자가 HWP 편집기를 만드는 대안을 질문했지만 이번 작업 범위는 기존 변환 앱 마무리로 유지했고 HWP 편집기는 만들지 않았다. 이후 “HWP를 PDF로, 다시 Word로 바꾸는 것인지”라는 질문에는 위 native 경로와 한글 PDF 출력의 수동 단계를 설명했다. [CLI 경로 명세](NATIVE_PDF_WORKFLOW.md), [웹 연결 보고서](NATIVE_WEB_REPORT.md) 참고.

### 바탕화면 실행 앱

사용자 요청으로 녹색 문서 로고의 **문서잇.app**을 생성해 Finder로 바탕화면에 배치했다. 아이콘 실행으로 기본 Chrome에 변환 화면이 열리는 것을 확인했다.

`scripts/launch_desktop.py`는 실행 중인 서버가 이 프로젝트 소유인지 확인하고 재사용한다. 서버가 없으면 기존 실행기를 독립 세션으로 시작하고 준비 상태를 기다린다. 다른 프로그램이 포트를 사용하면 종료하지 않고 오류를 표시한다. 프로젝트 `.venv`를 사용하며 시스템 Python과 로그인 자동 실행 설정은 바꾸지 않았다. 브라우저를 닫아도 서버는 백그라운드에 남는다.

### HWP → PDF 버튼 추가

사용자가 앱에 HWP → PDF 버튼이 없다고 요청해 별도 변환 유형을 추가했다. 설치된 엔진의 도움말과 실제 `convert --to pdf` 실행으로 지원을 확인하고 `HwpPdfEngine`을 등록했다.

```text
HWP → PDF 베타 선택
  → HWP 파일 업로드
  → PDF로 변환하기
  → 본문·이미지 존재 검사
  → PDF 다운로드
```

이 기능은 기준 PDF 첨부 없이 고정 CLI로 직접 PDF를 출력한다. **한글 뷰어의 PDF 인쇄와 다른 경로**이며 생성 PDF를 native 기준 캐시에 자동 등록하지 않는다. 사용자 실문서의 이전 원본 경로를 당시 다시 찾지 못해 이번 PDF 엔진의 실문서 시각 품질은 검증하지 못했다. 합성 한글/영문·표/병합·이미지·다페이지 PDF 및 브라우저 다운로드를 확인했다. [HWP PDF 보고서](HWP_PDF_REPORT.md) 참고.

### 원본 파일명 유지

사용자가 결과가 모두 converted라는 이름으로 저장된다고 지적해 전체 웹 변환에 원본 basename을 적용했다.

- 사업계획서.hwp → 사업계획서.docx 또는 사업계획서.pdf
- 월간 보고서.v2.pdf → 월간 보고서.v2.docx

한글·공백·괄호·중간 마침표를 유지하고 경로·제어 문자·금지 문자 및 과도한 길이를 정리한다. 서버 내부는 계속 고정 파일명을 쓰며 정리한 다운로드 이름만 작업 수명 동안 메타데이터에 저장한다. API의 `download_filename`, UTF-8 응답 헤더, Blob 다운로드와 화면 안내가 같은 이름을 사용한다. 재시작 후에도 이름을 유지하고 삭제/만료 시 제거한다. 이름을 저장하지 않았던 예전 작업은 다시 변환해야 한다.

### 버튼 배치와 새 파일 업로드

사용자는 업로드 버튼과 변환 버튼의 거리가 멀고, 완료 후 새 파일을 올리는 동선이 보이지 않는다고 요청했다.

파일 선택·변환 버튼을 업로드 영역 아래에 같은 줄, 12px 간격으로 배치했다. 완료 후 입력용 버튼 묶음 대신 다운로드 옆에 **새 파일 업로드**를 표시한다. 버튼 클릭은 바로 파일 선택창을 요청하며, 새 파일을 실제 선택하기 전에는 기존 결과를 유지한다. 선택창 취소와 같은 파일 재선택을 지원하고 오류 후에도 새 파일을 올릴 수 있다.

브라우저에서 PDF→Word 완료 → 새 파일 선택 요청 → HWP 선택 → HWP→PDF 완료를 확인했다. 데스크톱과 390px 모바일에서 버튼 간격과 가로 넘침을 검사했고, HWP native 기준 PDF가 없을 때 변환 버튼 비활성화도 유지했다.

## 실행과 운영

```bash
# 설치된 프로젝트에서 실행
npm run dev

# 이미 실행 중인 이 프로젝트 서버의 코드를 갱신할 때
npm run dev -- --restart

# 자동 테스트와 프런트엔드 구문 확인
.venv/bin/python -m pytest -q
node --check app/frontend/static/app.js

# 기준 PDF를 Word로 독립 변환할 때
.venv/bin/python scripts/convert_reference_pdf.py reference.pdf runtime/results/native-embedded.docx

# 같은 HWP의 한글 출력 기준 PDF를 24시간 등록할 때
.venv/bin/python scripts/register_native_reference.py source.hwp reference.pdf

# 현재 프로젝트 경로를 가리키는 실행 앱 생성: 기존 앱 덮어쓰기 없음
.venv/bin/python scripts/build_desktop_app.py
```

웹 주소는 **http://127.0.0.1:8000**이다. 바탕화면 아이콘으로도 실행할 수 있다. 프로젝트 폴더를 이동하면 실행 앱을 다시 생성해야 한다. 초기/전용 환경 설치는 [README](../README.md)를 따른다.

원본 파일은 수정·삭제하지 않는다. 업로드 복사본과 중간 파일은 작업 종료 후 정리하고, 실패 부분 결과는 제공하지 않는다. 성공 결과는 완료 후 1시간 보관하며 등록 기준 PDF는 별도 24시간 TTL이다. 입력 30 MiB, PDF 100쪽, 작업 동시 1개·대기 5개, 180초·RSS 1 GiB·작업 폴더 1 GiB 제한을 사용한다. 서버 중지 중 정리는 다음 시작으로 미뤄진다. CLI 결과와 수동 QA 산출물은 자동 TTL 대상이 아니다.

사용자 문서·글꼴·.venv·runtime·.tools는 Git에 포함하지 않는다. 클라우드, 외부 유료 API, 데이터베이스를 추가하지 않았다. localhost 단일 사용자용이며 공개 서비스의 인증·격리를 제공하는 배포 단계는 별도다.

| native 웹 연결 | 110 passed | 실제 HWP 업로드·기준 PDF 연결·DOCX 다운로드 |

마지막 행은 이 기록 작성 전 최신 코드 검증 결과다. 이 문서 저장 자체를 위해 변환 품질 테스트를 새로 실행한 것으로 표시하지 않는다. 기존 경고는 Starlette httpx 및 SWIG 관련이며 최신 실행의 실패/skip은 없었다.

아직 완료하지 않은 항목은 원본과 완전히 동일한 레이아웃, 모든 실문서의 Word 전 페이지 비교·편집/저장, 읽기 순서·모든 표/이미지의 정확한 대응, 한글 뷰어 PDF 출력 자동화, HWPX/OCR, Linux HWP·Docker 배포, HWP 편집기다. 다음 품질 검증은 실문서 corpus 확보, 한글 기준 PDF와 전 페이지 비교, 표 셀/이미지 대응 및 글꼴 환경별 회귀다.
